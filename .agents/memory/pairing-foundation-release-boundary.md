description: Scope and safety policy for the approved Development-only first phase of pairing consolidation.

Phase 1 of the shared pairing foundation and its approved Development message correction remain frozen. The user authorized offline contracts, mocked server integration, bounded synthetic safety verification, the specifically approved opt-in shared-service corrections, and the isolated synthetic UI exception below. The undeployed-Development advisor registration stays deny-by-default. Real profile execution, live or paid calls, customer-facing synthetic recommendations, and live advisor activation remain unauthorized.

**Why:** The user explicitly chose to close current development work and leave live verification pending until an eligible, authorized test account is available, rather than repeat known-blocked tests.

**How to apply:** Do not create accounts, change genuine restrictions, repeat blocked generation tests, or treat mocked integration approval as live activation approval. Keep existing screens, pairing routes, validators, DTOs, API compatibility and Production behavior unchanged; research, photo input, inventory integration and release work still require separate approval. Stop after each approved bounded verification increment for review.

The education-versus-consumption distinction is the approved Phase 2 design baseline. Reclassify intent on every turn, validate all response fields including alternatives and follow-up suggestions, and explain transitions into restricted consumption advice without misleading retry instructions.

**Why:** The user accepted the proposed design and explicitly added these three refinements before requesting a read-only integration blueprint.

**How to apply:** Educational explanation is not personal consumption clearance. Chat history cannot override saved safety authority or substantiate bottle ingredients, availability, prices or supplied-list membership. Keep live runtime implementation and paid execution paused until separately authorized.

Initial advisor scope is the authenticated account owner only. Missing required safety authority fails closed even for education; missing optional preferences is a separate concern. Newly disclosed relevant risks withhold personal advice without silently editing profiles. Approved offline attempt/deadline/error contracts do not authorize live operational settings.

**Why:** The user explicitly settled these design decisions while authorizing offline work only, keeping household resolution and operational settings for separate approval.

**How to apply:** Never infer another subject from chat or inherit active household selection. No unrestricted fallback or consumption instructions in educational prompts. Do not claim client memory preserves disclosures across reset or use mocked verdicts as evidence of real semantic accuracy.

The new advisor must use existing active-access AND Pro-access checks, with five submissions per account per minute and one in-flight submission per account. The application binding must remain deny-by-default, and an unproven complete/write-free authority path must remain unavailable.

**Why:** The user explicitly approved those limits and access requirements for mocked integration while prohibiting real customer reads/writes and synthetic recommendations to real users.

**How to apply:** Inject fixtures only in the isolated integration harness. Do not supply fixture or live dependencies in the application registration, change existing middleware, bypass required context to avoid persistence, or begin the conversational interface without separate approval.

Real deterministic scanner integration and strict account-owner verification are authorized only with synthetic profiles, envelopes, dependencies and mocked storage. The approved shared-service corrections are limited to no-save write accounting, explicit owner scope and required-source completeness. Existing callers must retain their default behavior.

**Why:** The user separately approved these three corrections for offline implementation while explicitly keeping the entry point disconnected and the application binding unactivated.

**How to apply:** Do not change scanners, clinical formulas, thresholds, activation rules or nutrient limits. Do not register the strict-owner entry point, query real profiles or start live verification. Additional shared-service scope, runtime activation and frontend work require separate approval; stop after implementing and verifying the authorized corrections.

The approved Development-only UI exception is to show Chef Pairings' specific `PAIRING_INGREDIENTS_UNVERIFIED` explanation instead of generic retry advice. Reviewing the HTTP classification does not authorize changing its contract.

**Why:** The user approved that narrow verification follow-up without changing safety policy, eligibility, authentication, subscriptions or clinical authority.

**How to apply:** Keep the message correction Development-gated. Account eligibility must come from genuine saved settings; never create accounts or remove restrictions to obtain a successful demonstration. Preparation-only instructions mean stop before paid execution.

**Why:** The user authorized a controlled foundation correction, not all five phases of the proposed advisor.

**How to apply:** Keep the implementation server-gated to an undeployed Development runtime. Apply authoritative context and complete output validation to the active Drink Pairing, Wine List Translator and Chef Pairings routes. Tighten the weaker routes; never establish parity by removing Drink Pairing's verified-ingredient gate. Education-versus-consumption policy remains a separate decision.

Wine-list selection must use unambiguous, complete supplied identities, including producer and vintage when present. An unverified Best Choice is withheld, not silently replaced by a different model choice.

**Why:** The prior translator trusted the model to select an actual listed wine. General wine knowledge and verified bottle composition or availability are different evidence.

**How to apply:** Do not substitute fuzzy name matching, model assertions or a safety PIN for source membership and eligibility. Treat unsupported or ambiguous inputs as needing clarification.

Use real scanner consumer tests as well as mocked route tests.

**Why:** A mocked alcohol scanner caught whiskey in alternatives, while the real generic scanner missed that alias. Passing mock contracts alone did not prove actionable-field coverage.

**How to apply:** Reuse the established beverage alcohol detector for already-authoritative alcohol prohibitions; do not add new clinical limits or change unrelated global validators as part of this foundation.

For bounded live verification, count provider attempts across both application retries and SDK retries, not just feature submissions.

**Why:** An initial pairing smoke-test estimate counted the application retry loop but missed the SDK's additional retries, understating the possible provider-attempt count.

**How to apply:** Establish a reliable total upper bound before submitting paid requests. If it exceeds the user's approved budget, stop rather than silently increasing the budget or changing frozen code or configuration.

An isolated, undeployed Development-only conversational UI prototype is approved using deterministic synthetic fixtures only. Freeform chat is primary; optional questions and context editing must not become a required questionnaire.

**Why:** The user separately approved the synthetic conversational experience while explicitly prohibiting customer entry points, live routes/providers, strict-owner activation, real profiles, database/schema/environment changes, Production changes, publishing, pushes and merges.

**How to apply:** Keep the prototype separate from the three existing pairing screens and exclude its private preview from builds, preview serving and deployed runtimes. Display-shape validation is not clinical authority. Keep the application binding denied and stop after prototype verification; customer integration or live activation needs separate approval.

Integration-readiness Increments A–C are a reviewed, frozen offline adapter/control checkpoint, not live activation approval. Keep the prototype unchanged, the existing Drink Pairing feature operating normally and the application advisor binding denied.

**Why:** The user reviewed the offline completion report and recommended freezing it. The next investment should prove that the intelligence works, not add infrastructure without a specific reason or begin another broad redesign.

**How to apply:** Before seeking D–F approval, define a narrow cost-controlled phase covering safe real-provider connection, medical-context re-establishment after expiry, and measured recommendation improvement. Preserve education versus consumption on every turn. Keep real strict-owner results separate from synthetic-only contracts. Do not claim cross-login, expired-session or process-restart disclosure continuity without separately approved storage. Offline success is not evidence of real language understanding, provider retry behavior or customer readiness.

The larger product objective is an AI advisor that understands food, wine, flavor, preparation, personal preferences and real-world context, not just generic wine suggestions.

**Why:** The user explicitly restated this objective while keeping the work limited to Phase 1 verification.

**How to apply:** Use this objective when separately authorized future intelligence work is scoped; it is not permission to begin live advisor execution.
