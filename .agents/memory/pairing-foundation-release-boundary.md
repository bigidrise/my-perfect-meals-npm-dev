Phase 1 of the shared pairing foundation and its approved Development message correction are now frozen. Current authorization is limited to designing the education-versus-consumption safety policy and Phase 2 conversational behavior, not implementing them. No additional implementation or paid testing is authorized.

**Why:** The user explicitly chose to close current development work and leave live verification pending until an eligible, authorized test account is available, rather than repeat known-blocked tests.

**How to apply:** Do not create accounts, change genuine restrictions, repeat blocked generation tests, or treat policy design as Phase 2 implementation approval. Keep screens, API compatibility and Production behavior unchanged; research, photo input, inventory integration and release work still require separate approval.

The education-versus-consumption distinction is the approved Phase 2 design baseline, not implementation approval. Reclassify intent on every turn, validate all response fields including alternatives and follow-up suggestions, and explain transitions into restricted consumption advice without misleading retry instructions.

**Why:** The user accepted the proposed design and explicitly added these three refinements before requesting a read-only integration blueprint.

**How to apply:** Educational explanation is not personal consumption clearance. Chat history cannot override saved safety authority or substantiate bottle ingredients, availability, prices or supplied-list membership. Keep coding and paid execution paused until separately authorized.

The approved Development-only UI exception is to show Chef Pairings' specific `PAIRING_INGREDIENTS_UNVERIFIED` explanation instead of generic retry advice. Reviewing the HTTP classification does not authorize changing its contract.

**Why:** The user approved that narrow verification follow-up without changing safety policy, eligibility, authentication, subscriptions or clinical authority.

**How to apply:** Keep the message correction Development-gated. Account eligibility must come from genuine saved settings; never create accounts or remove restrictions to obtain a successful demonstration. Preparation-only instructions mean stop before paid execution.

**Why:** The user authorized a controlled foundation correction, not all five phases of the proposed advisor.

**How to apply:** Keep the implementation server-gated to an undeployed Development runtime. Apply authoritative context and complete output validation to the active Drink Pairing, Wine List Translator and Chef Pairings routes. Tighten the weaker routes; never establish parity by removing Drink Pairing's verified-ingredient gate. Education-versus-consumption policy remains a separate decision.

Wine-list selection must use unambiguous, complete supplied identities, including producer and vintage when present. An unverified Best Choice is withheld, not silently replaced by a different model choice.

**Why:** The prior translator trusted the model to select an actual listed wine. General wine knowledge and verified bottle composition or availability are different evidence.

**How to apply:** Do not substitute fuzzy name matching, model assertions or a safety PIN for source membership and eligibility. Treat unsupported or ambiguous inputs as needing clarification.

Use real scanner consumer tests as well as mocked route tests.

**Why:** A mocked alcohol scanner caught whiskey in alternatives, while the real generic scanner missed that alias. Passing mock contracts alone did not prove actionable-field coverage.

**How to apply:** Reuse the established beverage alcohol detector for already-authoritative alcohol prohibitions; do not add new clinical limits or change unrelated global validators as part of this foundation.

For bounded live verification, count provider attempts across both application retries and SDK retries, not just feature submissions.

**Why:** An initial pairing smoke-test estimate counted the application retry loop but missed the SDK's additional retries, understating the possible provider-attempt count.

**How to apply:** Establish a reliable total upper bound before submitting paid requests. If it exceeds the user's approved budget, stop rather than silently increasing the budget or changing frozen code or configuration.

The larger product objective is an AI advisor that understands food, wine, flavor, preparation, personal preferences and real-world context, not just generic wine suggestions.

**Why:** The user explicitly restated this objective while keeping the work limited to Phase 1 verification.

**How to apply:** Use this objective when separately authorized future intelligence work is scoped; it is not permission to begin Phase 2.
