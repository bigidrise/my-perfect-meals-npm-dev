Stage 1 nutrition/serving work is authorized only in Development. Later dietary,
generation reliability, image and internal-error repairs require separate approval.
No Production changes, publishing, GitHub pushes/merges or migrations are authorized.

**Why:** The user prioritized ingredient-backed nutrition and explicitly separated
later repairs from this approval.

**How to apply:** Reuse the existing USDA/conversion infrastructure. Never replace
unknown nutrition with invented macros or zero, and do not infer frying absorption.

Repair 1 disclosure protection is accepted for continued Development work, not
Production release. Repair 2 alone is now approved: source-preserving cooking
instruction normalization, truthful course outcomes and completion, and validation
of cached incomplete recipes. Repairs 3–4 still require separate approval.

**Why:** The user accepted Repair 1 and separately authorized Repair 2 in
Development, explicitly requiring a stop afterward.

**How to apply:** Reject incomplete drafts without inventing recipe content.
Preserve nutrition, six-serving calculations, clinical withholding, and all
existing safety rules. Supported instruction normalization must not invent
directions. Failed and withheld courses never count as successful recipes.
Do not expand image behavior, badge validation, release baselines, or starch policy.

Phase A USDA resolver work is stopped. Do not integrate it into the active
Gatherings route, add USDA aliases, or expand ingredient normalization. Leave the
isolated implementation in Development without activating it.

**Why:** The experiment did not meet the integration prerequisite, and the user
explicitly closed this work in favor of restoring existing Gatherings functionality.

**How to apply:** Preserve Stage 1 nutrition safeguards and accurate six-serving
calculations. Do not change the release baseline or pre-existing starch-policy
failures. Wider generation reliability, image work and badge work remain outside
the approved instruction/outcome repairs.

Ingredient-coverage approval does not authorize guessing salmon identity, bone-in
ham edible weight, coconut-milk formulation, or hydrated wakame composition.
Keep those unresolved until defensible source evidence exists.

**Why:** The user explicitly retained these ambiguities during the targeted
Christmas ingredient-coverage repair approval.

**How to apply:** Keep active reviewed Gatherings mappings unchanged. Isolated
normalization must use source-backed identity and compatible portion evidence;
do not broaden shared generator matching or safety rules.

Event-specific dietary/cuisine selections are removed from the roadmap. Preserve
global profile personalization; do not add dietary/cuisine dropdowns to Gatherings
or Getaways.

**Why:** The user confirmed Vegan and Japanese global settings were reflected
successfully in both features and said additional selectors are unnecessary.

**How to apply:** Keep the existing profile workflow unchanged. Future event UI
changes require an explicit new request.

Do not retroactively label every legacy Create a Dish favorite as a Gathering.
Apply Gatherings-only nutrition restrictions to identifiable Gatherings records;
leave ambiguous historical origins unresolved rather than rewriting saved meals.

**Why:** Earlier Gatherings saves used the shared creator source label, and Stage
1 explicitly prohibits unrelated generator changes and database backfills.

**How to apply:** Preserve read-only recipe access and use exact origin evidence
or the established Gatherings course shape for the scoped nutrition gates.
