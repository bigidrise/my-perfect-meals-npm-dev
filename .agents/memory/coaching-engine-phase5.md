## What Phase 5 adds

Phase 5 closes the behavioral coaching loop with five new capabilities:

1. **Objective completion detection** — platform logs (water_logs, biometric_sample, macro_logs, platform_activity_events) are checked to confirm action item completion post-plan. `completionDetector.ts`.
2. **Subjective completion** — user reports completion via `POST /api/coach/plans/:planId/items/:itemId/complete`. Route calls `markSubjectiveCompletion()`.
3. **Memory extraction** — after each turn, non-blocking LLM pass proposes coaching memories. Server validates against per-category key allowlists before writing. `memoryExtractor.ts`.
4. **Bounded conversation continuity** — >20 messages: last 10 direct + rolling summary from coaching_memories. `conversationSummarizer.ts`.
5. **Follow-up worker** — cron every 10 min + inline delivery. Worker persists follow-up as a new assistant message in the original conversation. `followupWorker.ts` + `coachFollowupCron.ts`.

## DB changes (Phase 5 migration)

`runPhase5Migration.ts` — runs via setTimeout in both index.ts and prod.ts.

- `coach_action_items`: +`completion_source TEXT`, +`completion_confidence TEXT`
- `coach_followups`: +`observer_selection JSONB`, +`investigation_id UUID`
- Unique partial index: `CREATE UNIQUE INDEX IF NOT EXISTS coach_followups_plan_pending_uniq ON coach_followups (plan_id) WHERE status = 'pending'`

## Non-obvious rules

### Completion detection
- `unknown` is the only valid status when evidence is absent — NEVER set `failed`
- objective → high confidence; subjective → medium; unknown stays unknown
- `markSubjectiveCompletion` is idempotent; won't downgrade an objective high-confidence completion
- `completionSignal` values: `water_logged`, `weight_logged`, `meal_logged`, `macro_logged`, `restaurant_logged`, `beverage_logged`, `exercise_logged`, `self_reported`, `unknown`

### Memory extractor
- LLM PROPOSES, server VALIDATES — raw LLM output never goes directly to DB
- Key allowlist per category strictly enforced (see `ALLOWED_KEYS` in memoryExtractor.ts)
- Confidence threshold: 0.4 minimum to write
- Contradiction: archive old with `status='superseded'`, write new
- Duplicate (same key+value): silently skip
- Expiry limits: behavior/lifestyle 90d, nutrition 60d, success 180d (LLM can shorten, never extend)

### Conversation summarizer
- Threshold: >20 messages triggers bounded mode (last 10 direct + summary)
- Summary stored as `coaching_memories` with `key='conv_rolling_summary'`, `category='behavior'`
- Summary keyed by `conversationId` in value_json (not by user — each conversation has its own)
- Stale if >7 days; background refresh triggered, current turn still gets old summary
- Fallback: if summarizer fails, engine falls back to simple last-10 loading

### Follow-up worker
- Atomic lock: `UPDATE ... SET status='processing' WHERE status='pending' RETURNING id` — only one worker processes a followup
- If worker crashes, it resets to `pending` (try/catch at bottom of processFollowup)
- Follow-up message is a real `coach_messages` assistant row in the original conversation — user sees it naturally on next open
- CoachsCorner calls `GET /api/coach/followup/due` on load; if found, calls `POST /api/coach/followup/:id/deliver` to trigger inline delivery
- `alreadyDelivered: true` response = cron beat the UI; UI should refetch messages
- New follow-up plans generated by the worker can themselves create follow-up records (chaining)

### Engine integration points
- `persistTurn()` now takes `selectedObserverIds: string[]` as last param (was optional before Phase 5)
- `loadConversationHistory()` now returns `{ history, rollingContext }` instead of just an array
- `rollingContext` injected into reasoning pass as "EARLIER CONVERSATION CONTEXT (summarized, do not cite as evidence)"
- Memory extraction is **fire-and-forget** after persistTurn — never blocks the user response
- Follow-up row created immediately after plan INSERT, only if `followUpAt` is set in LLM response

### Schema conventions
- `coaching_profiles.coach_profile_completed_at` (NOT `completed_at`) — this is the intake completion flag
- `coach_conversations` requires `subject_type` and `subject_id` columns (not just owner_id + specialization)
- `db.execute<T>` drizzle-orm constraint: use `as unknown as T[]` pattern for typed row access

## What is NOT in Phase 5 (deferred)

- Phase 6: Pregnancy Coach integration, Product Intelligence, Supplement Scan
- Push notifications for follow-ups (cron + inline delivery is sufficient for now)
- Conversation summary refresh is background-only (current turn always uses last valid summary)
