My Perfect Meals
Shell Release Cheat Sheet

Development → GitHub dev → reviewed PR → GitHub production → Production workspace → Republish → Verify

Repository: bigidrise/my-perfect-meals-npm-dev
Source branches: dev and production

Release gate: This document is instructions, not release approval. Finish the required manual clinical acceptance before promoting the currently held clinical changes. A clean working tree or passing automated check does not approve every feature on dev.

What you can do without the GitHub website

You can create, inspect, and merge a GitHub pull request entirely from the Replit Development Shell using gh, GitHub's command-line tool. You do not need an agent for routine releases.

Keep the PR. This project's push policy intentionally rejects direct updates to production, main, and staging. Do not bypass the hook. Required GitHub checks, approvals, and branch rules still apply when using the CLI. Initial sign-in or organization authorization may require a browser.

Run the numbered stages separately. Stop on an error; do not continue to the next stage. The shell blocks do not force-push, reset, rebase, delete branches, publish automatically, or explicitly run database migrations or cleanup. Publishing starts the application's normal runtime, whose database effects require the normal release review.

1. Development Shell — check and push dev

Check the branch and changes:

git branch --show-current
git status --short --branch
git diff --check

The branch must be dev. If the working tree is clean, there is nothing new to stage or commit. Replit may already have committed the work in checkpoints.

If there are uncommitted changes, review and stage only approved files using Git's interactive menu:

git add -i
git diff --cached --stat
git diff --cached

Only after checking the staged contents:

git commit -m "Save reviewed Development changes"

If nothing is staged, skip that commit command. Do not use git add . blindly; it can include unrelated files. Unstaged or untracked files left in the working tree will deliberately block the guarded push.

Push with the project's established helper:

npm run push

This checks the branch, destination, clean working tree, and dev ancestry; runs npm run validate -- --no-start; rechecks the state; and pushes only local dev to GitHub dev. It does not commit files, promote production, or publish. Do not run ordinary validation first just to duplicate this check.

Confirm the actual remote result:

(
  set -eu
  git fetch --no-tags origin dev
  LOCAL=$(git rev-parse HEAD)
  REMOTE=$(git rev-parse origin/dev)
  printf 'Local:      %s\nGitHub dev: %s\n' "$LOCAL" "$REMOTE"
  test "$LOCAL" = "$REMOTE"
)

Pass: the two full commit IDs match. If the helper fails, no successful push is claimed. Do not substitute a raw push to bypass failed validation.

2. Development Shell — open or find the PR

The gh command is installed in the inspected Development workspace. Check its authorization:

gh auth status

If it is not authenticated, use the normal GitHub CLI login flow:

gh auth login --hostname github.com --web --git-protocol https

If an existing environment-managed token is selected or your organization requires approval, follow the reported authorization requirements. Never paste tokens or passwords into chat, commit them, or disable security rules.

Find an existing dev-to-production PR, or create one if none exists:

(
  set -eu
  REPO=bigidrise/my-perfect-meals-npm-dev
  PR=$(gh pr list --repo "$REPO" --base production --head dev \
    --state open --json number --jq '.[0].number // empty')
  if [ -z "$PR" ]; then
    gh pr create --repo "$REPO" --base production --head dev \
      --title "Development release review" \
      --body "Review the complete dev-to-production diff and required verification before merging."
    PR=$(gh pr list --repo "$REPO" --base production --head dev \
      --state open --json number --jq '.[0].number // empty')
  fi
  test -n "$PR"
  gh pr view "$PR" --repo "$REPO"
  gh pr diff "$PR" --repo "$REPO" --stat
  printf '\nREVIEWED DEV COMMIT CANDIDATE:\n'
  gh pr view "$PR" --repo "$REPO" --json headRefOid --jq .headRefOid
)

Save the full dev commit ID printed above. This is a candidate until you review it. A PR may include all differences between dev and production, not just the last task. If any included change is unfinished, unapproved, or held, stop. Prepare a separately reviewed release candidate instead of merging all dev.

Inspect the full diff and GitHub checks:

(
  set -eu
  REPO=bigidrise/my-perfect-meals-npm-dev
  PR=$(gh pr list --repo "$REPO" --base production --head dev \
    --state open --json number --jq '.[0].number // empty')
  test -n "$PR"
  gh pr diff "$PR" --repo "$REPO"
  gh pr checks "$PR" --repo "$REPO" --watch
)

Do not merge failed or pending required checks. If GitHub reports no checks, that is not a passing CI result: complete the project's required local validation and manual acceptance, and confirm no required check is missing. Local automated checks do not replace the release's required manual tests.

3. Development Shell — merge the approved PR

Only run this after reviewing the entire PR, completing required checks, and approving this exact release. At the prompt, paste the full reviewed dev commit from stage 2:

(
  set -eu
  REPO=bigidrise/my-perfect-meals-npm-dev
  PR=$(gh pr list --repo "$REPO" --base production --head dev \
    --state open --json number --jq '.[0].number // empty')
  test -n "$PR"
  read -r -p "Paste the fully reviewed dev commit SHA: " REVIEWED_HEAD
  test -n "$REVIEWED_HEAD"
  gh pr merge "$PR" --repo "$REPO" --merge \
    --match-head-commit "$REVIEWED_HEAD"
  printf '\nMERGE RESULT — SAVE THE PRODUCTION COMMIT:\n'
  gh pr view "$PR" --repo "$REPO" --json state,mergeCommit \
    --jq '{state: .state, productionCommit: .mergeCommit.oid}'
)

The commit match prevents silently merging additional dev commits added after your review. Use a merge commit to preserve the dev/production ancestry. Do not use --admin, force, squash, rebase, or delete the permanent dev branch as a shortcut.

Pass: state is MERGED and a production commit is printed. Save that full production merge commit, which is different from the dev commit. If queued, blocked, or not yet merged, wait and verify the PR state before proceeding.

GitHub production is now updated. The customer app is not published yet. No GitHub website visit was needed for the PR workflow.

4. Production Shell — fetch the exact approved release

Switch to the separate Production Replit workspace. This is not the Development Shell or Development Publish pane.

The following block requires a clean production branch, checks the GitHub release against your saved merge commit, and refuses to overwrite diverged history:

(
  set -eu
  test "$(git branch --show-current)" = production
  git status --short --branch
  test -z "$(git status --porcelain=v1 --untracked-files=normal)"
  git diff --check
  read -r -p "Paste the approved PRODUCTION merge commit SHA: " APPROVED_SHA
  test -n "$APPROVED_SHA"
  git fetch --no-tags origin production
  REMOTE_SHA=$(git rev-parse origin/production)
  printf 'Approved: %s\nGitHub:   %s\n' "$APPROVED_SHA" "$REMOTE_SHA"
  test "$REMOTE_SHA" = "$APPROVED_SHA"
  git merge-base --is-ancestor HEAD "$APPROVED_SHA"
  git merge --ff-only "$APPROVED_SHA"
  test "$(git rev-parse HEAD)" = "$APPROVED_SHA"
  printf '\nProduction workspace now contains approved source:\n'
  git rev-parse HEAD
)

fetch followed by merge --ff-only performs the two parts of a controlled pull, while pinning the exact approved commit. If GitHub has advanced to a different production release, stop rather than automatically deploying that newer code.

For this first use, confirm Production's origin is the same approved repository through its Git configuration. The Production workspace and remote were not inspected from this Development-only session.

5. Production Shell — validate and build

Run after successful synchronization. Each command must pass before continuing:

(
  set -eu
  npm ci
  npm run validate -- --no-start
  npm run check:safety-types
  NODE_OPTIONS=--max-old-space-size=4096 npm run check:release-types
  npm run build
)

npm ci installs the committed lockfile dependencies and runs their normal install hooks. The no-start flag avoids starting an extra validation server; it is not proof of live application health. The safety and reviewed-debt type gates are additional checks, not permission to bypass failed guarded-push validation.

Known source mutation: this project's build updates client/public/release-manifest.json and client/src/buildVersion.ts. Replit may also create publication/checkpoint commits. Do not automatically commit those changes to GitHub production, discard other changes alongside them, or assume the next pull will fast-forward.

Do not use npm run db:push, npm run serve, or npm run replit:start as routine deployment checks. The latter two have database-push prehooks in the inspected source. Development and Production share the external Neon database; any schema/data changes need their own reviewed plan.

6. Production workspace — Republish and verify

  1. Open Publishing in the Production workspace and choose Publish/Republish.
  2. Wait for the build and deployment to finish successfully. The configured publishing build runs npm run build again.
  3. Use the live URL shown in that Production Publishing pane—not a Development preview or Development published URL.
  4. Check /api/release on every customer domain you use. Compare its Git SHA with the approved production commit; the manifest normally records a shortened SHA. Confirm the new build timestamp/version.
  5. Open the customer app and verify sign-in and the release's critical changed flows. An HTTP 200 or correct SHA alone does not prove functional success.

Read-only live release inspection:

read -r -p "Paste the live Production URL from Publishing: " LIVE_URL
curl --fail --silent --show-error "${LIVE_URL%/}/api/release"

If publication changes the recorded build SHA to a new checkpoint commit, do not assume either success or failure solely from its name. Verify that checkpoint contains exactly the approved application source. Otherwise the release is not verified. Publishing starts the app's normal runtime; this sheet does not authorize extra migrations or maintenance commands.

If a command stops: do not force it

A dirty workspace, rejected push, failed validation, local-ahead history, or divergence is a reason to stop. The failed operation is not evidence that GitHub lost your code.

These Production commands inspect history without changing it:

git status --short --branch
git log --oneline --left-right HEAD...origin/production
git diff --stat HEAD origin/production

A safety branch can preserve the current committed position, but does not save uncommitted files or repair a divergence:

git branch "backup/production-before-sync-$(date +%Y%m%d-%H%M%S)" HEAD

Why this has recurred: publication checkpoints can add commits—even empty ones—and builds can change tracked files. A Production workspace may also contain genuine local fixes that never reached GitHub. Do not assume every local-only commit is disposable because its label says “Published.” Preserve and reconcile genuine fixes through the reviewed source workflow.

This checklist detects those cases; it cannot safely resolve every history conflict with a universal command. A longer-term separate publication-checkout workflow could reduce recurrence, but it has not been configured or verified by this document.

Storage and mobile boundaries

  • Git transfers committed code—not secrets, database contents, uploaded images, or storage buckets. Preserve Production's verified environment and storage bindings. The bucket names in the earlier sheet were not re-certified here.
  • Web publication updates an installed mobile app only where that installed version actually loads the Production web functionality. Do not assume every iOS or Android screen is remotely delivered.
  • Native code, plugins, permissions, bundled assets, or delivery-configuration changes may require Capacitor synchronization, native builds, testing, and Apple/Google releases. Native release instructions require a separately verified platform workflow.

Never: force-push, git reset --hard, git clean -fd, bypass hooks with --no-verify, use git push --all, or overwrite customer data/storage to make a routine release succeed.
