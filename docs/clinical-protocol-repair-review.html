Clinical Protocol Authority & Synchronization Repair

Development implementation updated — release remains on hold pending authenticated acceptance.

Approved safety decision implemented: metabolic-support, metabolic-stress, and inflammation-support remain advisory-only. Their measurements and advisory records are preserved; unsupported activation is rejected by the backend and not offered by the UI. They do not illuminate protocol indicators, change specialty conditions or builders, or claim applied nutritional adjustments. The live optional Anti-Inflammatory feature requires an explicit opt-in; no live implementation established that a CRP recommendation grants that opt-in. A shadow mapping was not used as authorization. This is an intentional safe outcome, not a request for invented guidance.

What the draft changes

  • Shared compatibility identities normalize Cardiac and Renal aliases while retaining unknown saved values and keeping distinct protocols separate.
  • Lab acceptance checks subject-owned saved measurement evidence and eligibility. Activation and exact removal update protocol state transactionally without changing builders or studio membership assignment.
  • Ordinary nonclinical trainer builder assignments no longer establish physician authority. Explicit physician Oncology and verified assignment evidence remain protected; ambiguous clinical builder assignments require review.
  • Cardiac reassessment requires an active Cardiac protocol and uses qualified language about the measurements assessed, without claiming that a disease resolved.
  • Rejected backend decisions leave the three decision dialogs open with errors and do not invoke success callbacks.
  • A subject-keyed, status-only endpoint and query connect the six builders, professional dashboards, folder, and member status bar without exposing raw measurements.
  • Detailed clinical-data access reuses the established verified-clinician, relationship, organization, and consent policy instead of treating any studio owner as clinically authorized.
  • The existing indicator markup, grouping, and color tokens are retained. No new Pregnancy or GLP-1 indicator was added; the existing physician Hormone Optimization indicator was inspected rather than duplicated.
  • Supported lab signals no longer silently reactivate nutrition when the member saves an unrelated specialty choice. Explicit accepted choices, not raw measurements, own activation.
  • Clinical ownership decisions now commit in the same transaction as member profile changes and physician Hormone/Thyroid writes, using the existing decision-audit table and reserved server-owned reasons. Client attempts to forge those reasons are rejected.
  • Known physician ownership survives relationship removal. Known member ownership does not itself create a physician lock. Unattributed Clinic-linked settings require review rather than being backfilled with invented ownership.
  • Thyroid subtype metadata narrows an active Thyroid support without independently activating nutrition. Physician-owned inactive settings remain protected without lighting an active-support indicator.
  • The Anti-Inflammatory Builder's obsolete asynchronous mode effect and dummy setters were removed. Mode, namespace, and modifiers use the same verified protocol state, retaining established precedence and clearing stale macro flags.

Verification boundaries

  • Frontend and backend builds, strict safety slice: passed after the provenance changes. New safety-sensitive surfaces were added to the strict safety configuration.
  • Deterministic checks: all 389 tests across 16 suites passed. They cover all 17 identities, supported guidance, the two obsolete source contracts, actual mutation callbacks, audit records, advisory-only controls, Cardiac reassessment, clinical-mode precedence, ingredient final scans, and privacy/consent boundaries.
  • Source-contract repairs: the profile test now follows the actual centralized allowlist; the ProCare test follows the invitation facade into the shared acceptance service, where the existing entitlement check still runs. These changes preserve the behavioral expectations rather than removing the guards.
  • Release type gate: the reviewed historical 109-diagnostic fingerprint was reproduced exactly. All current diagnostic locations were mapped through the source diff; reconstructing the reviewed set reproduced the exact original hash. Only two unchanged errors moved by three lines. No diagnostic messages, columns, or multiplicities changed. The baseline was updated only after that proof; no errors were suppressed or accepted. See the companion fingerprint-review document.
  • Runtime: the Development app starts under its existing safe-restart mode with automatic maintenance suppressed. The browser loaded the signed-out welcome screen. A secure sign-in handoff was offered but timed out. No authenticated member, trainer, or physician journey is claimed.
  • No full live lifecycle attestation: join/leave, multi-organization switching, re-login, and complete six-builder generation need remaining acceptance verification. Pure state tests do not establish those flows.

Remaining safety and implementation limits

  1. Authenticated acceptance remains blocked: approved member, trainer, and physician sessions are required to exercise all six builders and professional dashboards. A signed-out screenshot and mocked database tests are not substitutes.
  2. Historical provenance is not invented: older records without reliable ownership evidence cannot be retrospectively identified as physician- or member-owned. Ambiguous Clinic-linked settings stay review-required. No migration or blanket ownership backfill was performed.
  3. Runtime generation is unclaimed: guidance construction and deterministic final scans were tested without model calls. No paid six-builder recipe generation or real clinical-record mutation was performed.
  4. Relationship lifecycle evidence is bounded: synthetic tests cover active versus disconnected/archived relationships, organization/owner isolation, subject switching, and physician ownership after disconnection. Actual account join/leave/re-login and multi-organization browser journeys remain part of the pending authenticated acceptance.

Database and release impact

No schema migration or backfill was run. No production modification, publication, GitHub push, paid AI generation, or clinical threshold change was performed. Ownership is recorded only for future explicit authorized changes; existing records are not rewritten merely by reading them. Verification used deterministic synthetic fixtures and mocked database operations, not live clinical-record mutations. Source changes remain in Development.
