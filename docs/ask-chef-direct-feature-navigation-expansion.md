# Ask Chef — direct-feature navigation expansion

## Development scope and result

The registry now contains **36 approved destination IDs**: the original **22**
plus **14 additions** from the founder's requested list. Existing destinations,
subscription rules, application routes, lifecycle flags and clinical rules were
not replaced.

Twelve additions open independently routable features. Following the founder's
subsequent approval, the two modal-based additions open their actual parent,
Dashboard, and tell the member which modal to select. They do **not** automatically
open a modal or imply that it is already open.

No branches, worktrees, commits, pushes, merges, deployment or Production
modifications were performed. These are Development workspace changes.

## Concise behavior

- **Destination question:** one short offer, with no navigation button yet.
- **Acceptance:** verified directions and one button, then stop.
- **Direct command:** verified directions and button immediately.
- **Explanation:** brief answer without assuming consent.
- **Modal-based features:** offer their Dashboard location, then use the honest
  **Open Dashboard** parent action. The member opens the named modal themselves.

The exact question “Where can I see my saved meals?” now binds to Favorites:

> You can find them in **Favorites**. Would you like to go there?

After “Yes,” Chef provides **More → Favorites** and **Open Favorites**, without
another question. “Take me to Saved Meals” and “Take me to Favorites” produce the
same approved action.

For Recipe Maker, acceptance or a direct opening command produces:

> Open **Dashboard**, then select **Recipe Maker**.
>
> **Open Dashboard**

Sources & Medical Information uses the same pattern with its own modal name.
No modal state, recipe, information-sheet state or request content is transferred.

## Preserved authorization and safety

`POST /api/coach/navigation` still authenticates the member and executes the
destination's current access middleware before returning its fixed route.
`CoachFeatureAction` still verifies the returned ID and exact route before
navigating, displays authorization failures without leaving the conversation,
and sends its receipt only after observing the expected browser location.

The two Dashboard intents share a URL but retain separate IDs and receipts.
A bare `/dashboard` URL cannot identify which modal the member meant.

Clinical care/red-flag precedence, physician assignments, child/animal ownership,
30-minute offer expiry, original offer timestamps and owner-scoped receipt
persistence were not weakened. Food, alcohol, clinical and veterinary workflows
still run their existing checks inside their original destinations.

Automatic emphasis still uses registry-owned feature and navigation labels.
Neither page navigation nor a receipt proves that a workflow completed, a recipe
was saved, a clinical action was authorized or a modal opened.
