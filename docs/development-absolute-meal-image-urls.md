# Prepared Development-only absolute meal photograph URLs

## Status and activation boundary

Prepared for compatibility investigation of the user-confirmed iOS release
1.0.150. **Not activated.** No environment settings, workflows, native assets,
database records or storage objects were changed. This is not proof of the
code packaged in that release.

The adapter requires both:

- `NODE_ENV=development`
- `DEVELOPMENT_ABSOLUTE_MEAL_IMAGE_URLS=true`

The new flag is unset by default. `NODE_ENV=production` is always inert,
including a published Development runtime. This is deliberately not a
Production activation path. No configuration should be changed as part of
this preparation.

## Trusted public origin

When explicitly enabled, the origin is `https://${REPLIT_DEV_DOMAIN}`, using
the runtime-managed workspace hostname. The hostname must be a bare
`.replit.dev` hostname without credentials, a port, path, query or fragment.
No request Host, Forwarded, X-Forwarded-Host, Origin or Referer header is used.
Production application URL settings are not consulted.

The storage context must resolve to Development's canonical bucket. A
missing/invalid hostname, Production bucket, foreign URL or path traversal
fails closed; there is no fallback to Production or to a request hostname.
The exact bucket/object path is retained and delivered through the
Development server's existing `/public-objects/*` route.

This proves URL routing using mocked delivery, not live workspace
reachability, public access, CORS behavior or current object availability.

## Storage and response contract inventory

`publicMealImageUrl()` remains relative. Its three direct consumers are:

1. `permanentImageStorage`: upload return URLs used by generation/cache code.
2. `mediaAssetService`: canonical media display/thumbnail URLs.
3. `mealImageAuthority`: canonical object identity after authority checks.

Changing this function globally would change persisted references and
relative-only authority/cache classification. The new adapter instead copies
explicit image endpoint responses, after generation/cache work is complete:

| Response | Enabled Development behavior |
| --- | --- |
| `POST /api/meals/generate-image` | Matching absolute `imageUrl` and `imageResult.url`; includes both the shared router and duplicate registration in `routes.ts`. |
| `POST /api/generate-image` | Matching absolute legacy `imageUrl` and typed evidence URL for successful photographs; existing error envelope remains on failure. |
| `POST /api/meal-images/generate` | Absolute `image.url` and `image.imageResult.url`; success follows the serialized evidence. |
| `POST /api/meal-images/generate-batch` | Absolute matching URL fields for each verified image; metadata/count preserved. |
| `POST /api/meal-images/cached` | Copies the cached response without mutating its cache entry, key or recipe metadata. |
| `POST /api/meal-images/hydrate-with-image` | Converts only a photograph generated by this request; existing supplied/saved photographs are unchanged. Recipe success remains independent of photograph success. |

The legacy `imageUrl` field is retained wherever it existed. Failed,
unverified or missing photographs have null deliverable URLs in enabled
responses, never fallback artwork presented as photographic success.
Verification, generation, persistence and failure evidence are not upgraded.
A disagreement between the main URL and evidence URL fails closed.

Internal generator return values, memory/DB cache entries, object names,
media IDs and saved-photo rows are not converted. An exact Development
transport URL returning through `processImageForMeal()` or
`parseMealImageObjectUrl()` is normalized to its original relative path
before existing classification/authority checks. This prevents re-download,
re-upload or a new object identity solely due to the transport URL form.
Existing lifecycle rules still decide whether a normal save creates a media
record; the adapter does not itself save anything.

Deliberately unchanged: inline recipe-generation responses, attach/persist
endpoints, saved-photo reads, recovery endpoints/status, statistics, and
other legacy image forms (S3, data URIs or local artwork). No historical
rewrite, recovery request or generation retry is introduced.

## Verification

All new tests use synthetic origins, paths and image evidence. HTTP tests
use an isolated Express app, mocked generators/context and mock delivery.
The save-round-trip test mocks database insertions, object storage, image
processing and authority checks; no real write occurs.

```sh
npx jest --runInBand --globals='{"ts-jest":{"isolatedModules":true}}' \
  server/tests/developmentMealImageUrls.test.ts \
  server/tests/developmentMealImageUrlRoutes.test.ts \
  server/tests/developmentMealImageUrlIdentity.test.ts

npx tsc --noEmit --skipLibCheck --target es2022 --module commonjs \
  --moduleResolution node --types node \
  server/services/developmentMealImageUrls.ts
```

Coverage includes remote HTTPS and `capacitor://localhost` document bases,
matching legacy/typed URLs, spoofed request headers, invalid configuration,
Production isolation, cache immutability, same-object save round trips,
unverified/missing photographs and mocked 404 delivery without recovery.

Preparation result: all 33 new tests passed. The focused helper TypeScript
check and syntax diagnostics for changed TypeScript files also passed.
This was not a full-project type check or an installed-device test.

Additional regression suites examined: `apiRoutingStorageRepair`,
`mealImageAuthority`, `pediatricImageEndpoint`, `flareDevelopmentPreparation`.
The routing/storage suite has an unrelated existing assertion expecting
`app.myperfectmeals.com` while the configured API origin is
`app.myperfectmeals.ai`. Neither the API origin nor that assertion was changed.

## Remaining compatibility limits

- No archive/client bundle identifies the exact 1.0.150 implementation yet.
- Its actual request endpoint, timeout, response parsing, save path and WebView
  network policy remain unverified. An older inline-generation consumer is
  outside this adapter's explicit endpoint scope.
- A usable HTTPS origin does not fix a missing object, failed generation,
  verification failure or old client timeout.
- Current client recovery classification does not recognize this new
  first-party absolute URL form. Recovery is intentionally not changed or
  triggered. Saved responses remain canonical/relative under this stage.
- Later activation or expansion to Production requires separate approval,
  trusted Production-origin configuration, and review of every additional
  response/save/recovery path. Do not enable this Development-only flag in
  place of that review.
- Flare's existing activation and spending controls remain separate and
  unchanged.
